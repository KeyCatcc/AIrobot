# 多阶段 Agent 开发计划

> 状态：V1.0，2026-11-13  
> 目标：在不牺牲机器人安全性、实时性和可验收性的前提下，逐步从单次语义动作决策演进到受约束的任务规划。

---

## 1. 总体结论

自由规划型 Agent 是接待/导览机器人未来有价值的能力，但不是当前阶段的优先事项。

当前应继续采用：

```text
单次语义动作决策 + 状态机 + 受限 Tool + 动作执行服务
```

原因：挥手、点头、左右指引、对话伴随手势、主动问候、人脸跟随和待机动作，都要求低延迟、可预测、可中断。让 LLM 为每一步自由规划反而会增加延迟、误触发和难以验收的风险。

无论未来 Agent 发展到何种程度，LLM 都不能直接输出 ROS Topic、关节角度、串口指令、动作文件路径或任意 Shell 命令。

---

## 2. 当前阶段：单次语义动作决策

### 目标

让机器人根据用户原话和机器人回复内容，选择一次安全、白名单内的动作。

### 当前链路

```text
用户原话 + 机器人回复前缀
        ↓
云端 Qwen（结构化语义判断）
        ↓
{ gesture, source }
        ↓
RAI 校验：白名单、禁止条件、去重、超时、忙碌状态
        ↓
perform_gesture Tool
        ↓
动作 HTTP 服务 → ROS 2 → 电机
```

### 当前 LLM 职责

- 理解用户是否明确提出动作要求；
- 理解机器人回复是否适合搭配伴随动作；
- 在动作白名单中选择一个动作或 `none`；
- 标记来源：`user_request`、`reply_accompaniment` 或 `none`。

### 当前 RAI / Runtime 职责

- 校验结构化输出；
- 不接受白名单之外的动作；
- 处理禁止动作意图；
- 同一轮对话去重；
- 检查动作服务是否忙碌；
- 检查决策是否超时；
- 将动作标签转换为受控 Tool 调用。

### 不做的事

- 不让 LLM 调用 ROS Topic；
- 不让 LLM 输出电机角度；
- 不让 LLM 直接执行动作文件；
- 不引入行为树与 Agent 双重编排；
- 不把人脸跟随等高频控制循环暴露为 Tool。

### 当前验收目标

- 用户说“请向我挥手”时，选择 `挥手/招手`；
- 普通事实回答、引用、否定、明确禁止动作时不误触发；
- 云端单次决策延迟在接待互动可接受范围内；
- 动作服务只接收已开放且已验收的动作；
- 动作执行通过 ROS bridge 到达真机并回中性位。

## 3. 阶段二：感知与交互状态机

### 目标

使机器人能够基于环境状态自然互动，而不是只被动响应语音。

### 新增能力

- 人脸检测与最大稳定人脸选择；
- 保守的人脸跟随：死区、限速、丢失回正、头部动作让位；
- 主动问候：检测到稳定新访客时只问候一次；
- 待机动作：最低优先级、可随时让位；
- 交互状态机：`Idle / Attention / Greeting / Conversing / Farewell`。

### 边界

```text
感知：看见谁、位置在哪里
状态机：当前是否该跟随、问候、待机
控制器：如何平滑转头、如何回正
RAI：仅在需要理解语义时选择离散动作
```

人脸跟随、目标切换、回正和待机动作都不做成 LLM Tool；它们运行在 Runtime / 状态机内。

### 当前控制通道与后续演进

当前真机 bridge 只订阅一个 `/joint_states`。因此阶段二先采用**控制权让渡**：任何 RAI 身体手势开始前，头部跟随释放自己的 `/joint_states` Publisher；动作结束后，头部跟随再恢复。这样始终只有一个发布者，优先保证当前接待展示安全、稳定。

后续单列为“控制通道拆分”开发项，不在当前版本改 bridge：

```text
/head_joint_states        仅 neck_yaw_joint / neck_pitch_joint
/upper_body_joint_states  腰、肩、肘、手部等非头部关节
bridge                    订阅两路消息，按关节归属合并后唯一写入电机
```

拆分后，头部跟随可与非颈部手势并行；但仍必须保留仲裁机制。凡是包含颈部的全身动作、欢迎动作或异常恢复动作，头部通道仍需让位。实施前需要完成 bridge 的双话题订阅、关节归属表、合并优先级、超时回退以及真机回归测试。

### 验收目标

- 稳定人脸才触发跟随；
- 中心死区内不抖动；
- 丢失人脸后延迟回正；
- 点头、摇头与跟随不争抢头部通道；
- 同一访客在冷却期内不重复主动问候；
- 待机动作会为对话、欢迎和手势动作让位。

## 4. 阶段三：Skill 编排

### 目标

把多步但流程明确的互动固化为可验收 Skill，而非让 LLM 自由临场拼接底层操作。

### 首批 Skill

```text
greet_visitor
  = 面向访客 + 欢迎动作 + 欢迎播报 + 切换到 Attention

guide_exhibit
  = 导览起始播报 + 路线/展品介绍 + 指引动作 + 结束询问

answer_and_gesture
  = 回答问题 + 可选伴随动作

farewell_visitor
  = 告别播报 + 告别动作 + 回到 Idle
```

### Skill 与 Tool 的关系

```text
Skill：完成一个可理解的任务流程
Tool：执行一个原子、受限、可审计的能力
```

例如 `greet_visitor` 可使用：

```text
head_follow_controller（内部控制，不是 Tool）
perform_gesture("欢迎您")
speak("欢迎来到展厅……")
interaction_state.transition("Attention")
```

### 验收目标

- Skill 的输入、输出、失败和降级策略明确；
- Skill 不泄露 ROS、硬件或动作文件细节给 LLM；
- 任一步失败可安全结束或降级为仅播报；
- 每个 Skill 可脱离 duplex 用文本输入回归测试。

## 5. 阶段四：受约束的任务规划 Agent

### 何时引入

只有出现以下真实需求时才引入：

- 用户一句话包含多个连续目标；
- 导览过程会被打断、暂停、恢复或改路线；
- 需要在导航、知识库、视觉、预约登记等多个 Skill 之间选择顺序；
- 需要根据每一步执行结果调整后续动作。

### 典型场景

```text
用户：带我参观具身智能相关产品，
      中途我想看一下左边那台设备，
      最后帮我预约一个演示。

规划：
1. guide_to_exhibit(category="具身智能")
2. 用户打断后暂停原任务
3. explain_exhibit(location="left")
4. resume_or_finish_guide()
5. create_demo_reservation()
```

### 规划输出边界

规划 Agent 只能输出白名单内的 Skill 计划，例如：

```json
[
  {"skill": "guide_to_exhibit", "args": {"exhibit_id": "A01"}},
  {"skill": "explain_exhibit", "args": {"exhibit_id": "A01"}},
  {"skill": "speak", "args": {"text": "您还想了解其他内容吗？"}}
]
```

禁止输出：

```text
任意 ROS Topic
关节角度
串口命令
动作文件路径
任意 Shell 命令
绕过动作服务的硬件指令
```

### Runtime 必须补齐的能力

- 任务账本与任务 ID；
- Skill 前置条件校验；
- 超时、取消、重试与降级；
- 手势、语音、导航、头部控制的资源仲裁；
- 用户打断后的暂停、恢复或终止；
- 每一步结果、Trace ID 和可追溯日志；
- 人工授权和高风险动作白名单。

### 验收目标

- Agent 只能选择已注册 Skill；
- 计划每一步都能被 Runtime 拒绝、暂停或取消；
- 一步失败不会继续执行危险后续步骤；
- 用户打断后不会重复执行旧任务；
- 可以清晰复盘“为什么选这个 Skill、执行了什么、为何失败”。

---

## 6. 阶段五：多 Agent 协同（远期）

多 Agent 不是当前必需条件，只有当单 Agent 的上下文、工具数量和职责边界难以维护时才引入。

潜在角色：

- 对话 / 接待 Agent；
- 导览 / 任务规划 Agent；
- 知识检索 Agent；
- 感知 Agent；
- 安全与资源仲裁服务。

即使进入多 Agent 阶段，感知、实时控制和硬件安全仍不应完全交给 Agent 通信，而应由独立 Runtime 与安全策略兜底。

---

## 7. 每阶段的决策口诀

```text
阶段一：先把一个动作选对。
阶段二：让机器人在恰当时机自然地动。
阶段三：把稳定互动固化为 Skill。
阶段四：让 Agent 在白名单 Skill 内规划。
阶段五：只有复杂度真的需要时才拆多 Agent。
```

## 8. 当前下一步

3. 建立 `Idle / Attention / Greeting / Conversing / Farewell` 交互状态机；
4. 实现 `greet_visitor` 第一个完整 Skill；
5. 再逐步添加待机动作和更多伴随手势。
